- **[2026-09-18]**:
  - **One unit for knowledge points, and a session total that adds up.** Reported: the total gain shown above the session ticker does not move by the amount the row beneath it just showed, the total mixes a `+` and a `-` figure, and percentages and absolute points appear side by side. All three were real and had one root: `calculateMasteryPercentage` spans **0..200** (the MasteryRing's two visual loops) while `KNOWLEDGE_POINTS_PER_ENTRY` was **100**, so `entryKnowledgePoints` halved everything. The ring advanced 6, the ticker printed "+6%", the total moved by 3.
    - Fixed by setting the point scale equal to the mastery scale (`KNOWLEDGE_POINTS_PER_ENTRY = 200`, `entryKnowledgePoints` collapses to the identity). The scale is arbitrary, so the right choice is the one that removes every conversion; rescaling the *ring* to 0..100 would unify just as well but would throw away the deliberate two-loop design, so the scale moved rather than the ring. The ticker now prints points (no `%`), and the total is their plain running sum.
    - The total is now a **single net number** instead of a gained/lost pair, with the breakdown in the tooltip. Two figures side by side invite reading "+18 / -5" as one quantity.
    - Grammar answers now also report the points they credited to the sentence's **vocabulary** (`+N vocab`), measured by diffing the learning queue rather than re-deriving from `vocabCredits`, so it reports what was actually written (reinforcement is skipped entirely on a retry, and skips words absent from the queue).
    - Visible consequence, accepted: the Stats knowledge curve's absolute numbers double. The shape and every comparison drawn from it are unchanged.
  - **Wrong conjugation of the right verb now earns partial credit instead of full marks.** A vocab blank's accept-list was built from the occurrence's surface *and* the vocab's dictionary forms, so answering 思う where the sentence needs 思っ graded `correct` - the conjugation is much of what a cloze sentence tests, and getting it wrong was free. The dictionary forms now go to the existing `acceptListsMinor` tier (`minor_error`) instead.
    - Gated on `GrammarExampleWord.baseForm`, which the dataset sets **only when the base form differs from the surface**, so it is exactly an "this occurrence is inflected" signal. For an uninflected word nothing moves and writing 寿司 as すし stays fully correct.
    - The realization-variant path merges into `acceptListsMinor` rather than overwriting it, or a variant-group turn would silently restore full credit for wrong conjugations.

  - **Grammar cards can no longer be blocked: Submit is not gated on every blank being filled.** Reported from staging: revealing the last remaining blank with its hint button left Submit disabled and the card stuck with no way forward. Direct cause was a state/display divergence - the card rendered `revealed ? acceptLists[i][0] : answers[i]`, so the input showed the accepted form while `grammarAnswers[i]` stayed empty, and `canSubmitGrammar`'s "every answer non-empty" check never passed. Fixed at the root (`GRAMMAR_REVEAL_HINT` now writes the revealed form into `grammarAnswers`, and the card reads state directly), but the more useful change is removing the gate itself.
    - **This is the third distinct bug whose only symptom was an unsubmittable card**, after a multi-token pattern marker split across one input per token (see `blankWordSpans`) and blank indices from one sentence applied to another realization (see `GrammarQuizState.example`). The individual causes were unrelated; the shared failure mode is that requiring every input non-empty converts *any* blank-selection or hint defect into a hard block. A gate that turns unrelated bugs into dead ends is not worth what it buys.
    - An empty blank is now a supported answer meaning "I do not know this one", graded `'pass'` (-0.15, the same as a literally typed "pass") rather than `'wrong'` (-0.40): the learner skipped rather than mis-recalled, and the accepted form is revealed in the feedback, which is what the hint button was being used for. Auto-advance still requires every blank strictly correct, so a skipped blank always pauses on the answer rather than scrolling past it.
    - The pre-existing test asserting an empty blank grades `'wrong'` was updated rather than worked around: it encoded the old world where an empty blank could only mean a broken card, since it was unsubmittable by construction.

  - **The production quiz shipped but never actually ran.** Reported from staging a day after release: the same words kept coming up for reading and meaning, production never appeared once, and no production date was visible anywhere. Three separate causes, only the first of which was the interesting one:
    - **The session's committed set gates what can be *served*, so filtering it hides work permanently.** `filterSessionCommit` drops a word's non-reading tasks when its reading is committed, because a correct reading answer staggers them 12h out and counting both credits one answer with clearing two tasks. That was harmless while the set only fed the progress counter. The session cap made the set authoritative over selection, and the same filter then meant a dropped task could never be shown at all. Measured on staging: 15 tasks actionable (5 reading, 5 meaning, 5 production), 5 committed. Fixed by keeping the committed set unfiltered and moving `filterSessionCommit` to `selectSessionStats`, which is the only place that ever needed it. Note this also silently affected **meaning** in the same way: a *wrong* reading answer does not stagger meaning, so a genuinely-due meaning was unanswerable for the rest of that session.
    - **A fixed stagger cannot work for production the way it does for meaning.** Meaning resurfaces on its own because its interval soon diverges from reading's. Production is seeded against reading's own cadence, so for a daily reviewer the two stay due together, the +12h push repeats every session, and production is deferred forever. Removed the reading to production stagger entirely: never asking it is worse than the redundancy, and selection already serves production last, well after that word's reading. (Reading and production do share the same answer, so this is a deliberate trade, not an oversight.)
    - **Nothing in the UI showed a production date**, so even a correctly-seeded entry looked like a dead feature. The detail page's Next Review list now carries a production row reading "Not started" until activation, and the history graph gains a production series once there is one.
  - **Testing lesson worth keeping**: the unit tests passed throughout, and the staging walkthrough that verified the release checked seeding and one answered card but never the case where all three directions are due at once, which is the steady state for an existing user. A feature that is gated by scheduling needs a test at the point where its schedule collides with the existing ones, not just at first activation.

- **[2026-09-17]**:
  - **JLPT level matching widened past the kanji headword (dataset repo).** Investigated from a user report that かばん (vocab `1208910`) carried no JLPT level despite being obvious N5. The lookup keyed solely on JMDict's kanji headword (`jlptVocab[kanjiText]`), and the Bluskyo list files words under the form they are normally *written* in, which disagrees in two ways: orthography variants (its 近付く vs JMDict's 近づく) and usually-kana (`uk`) words, where 鞄 appears only as かばん and there is no kanji key at all to find. Now `resolveJlptLevel` (`scripts/build-common.ts`, unit-tested) tries every written form, then the readings. Worth keeping:
    - **Written-form hits and reading hits are deliberately not treated alike.** A written-form hit accepts the dataset's own fallback entry, but a reading key is accepted *only* when the matched entry's reading equals the word's primary reading. Readings are far more ambiguous than spellings, and a loose reading match hands 紙's N5 to every rare homophone read かみ. That restriction is what keeps a third bucket of candidates unmatched, and dropping it was measured rather than argued: building with a loose reading match adds exactly 23 words, and the evidence behind essentially every one is bogus. They match through a JMDict *alternative* reading that happens to spell an unrelated JLPT entry. 父 is listed nowhere in the source (neither 父 nor ちち), and picks up N4 from ちゃん, which JMDict carries as one of its alternative readings; 牡丹/ぼたん takes ボタン (button) N5, 南瓜/かぼちゃ takes なんか N1, 有界/うかい takes うがい (gargle) N3. Several land on a plausible-looking level by coincidence (蛇 N5, 父 N4), which is what makes this tempting and why the per-word evidence matters more than the totals. A narrower variant restricted to the primary reading is no better: its one hit is 寝/ね against a source entry whose reading field is the literal string `（感）`. Do not revisit without new evidence.
    - **Resolution runs before homograph merging, and moving it after would be a regression.** Measured blast radius came out 466 rather than the 489 predicted from compiled output; the 23-word gap is entirely words whose matching form arrives via a *merged* homograph. JMDict `1223610` is 貴方/きほう alone; its 貴女/あなた forms are merged in later, and inheriting あなた's level for a different word that merely shares a spelling is exactly the homophone error the reading rule exists to prevent. The prediction was wrong, not the build.
    - **Blast radius**: 466 words gained a level (N1 203, N2 88, N3 77, N4 45, N5 53), **0 lost one**, 1 changed (悪口 N1 → N3, from the improved tiebreak preferring a listed alternative reading over the dataset's arbitrary first entry - わるくち is the common N3 word, so this is a correction). Every other one of the 35,814 compiled vocab files was byte-identical after a full rebuild, which also re-confirms the build is deterministic.
  - **Production quiz (English meaning prompt, Japanese reading answer), added as a third vocab quiz type with its own SRS entry.** The app had no production direction at all: both existing quizzes prompt in Japanese, so nothing ever tested recall *into* Japanese. The design problem was never the card, it was adding a third direction to queues that already hold thousands of words without multiplying anyone's daily workload overnight. What is worth keeping:
    - **The rollout is lazy by construction, not by a tuned backfill.** `newSRSEntry` already yields `dueDate: null`, and every due-check requires a non-null `dueDate`, so a migration that fills in the entry makes **nothing** due. Activation instead happens in `SRSService.seedProductionEntry`, called when a word is answered in any *other* direction, so the new direction rides each user's existing review curve and spreads over one full cycle. A word reviewed monthly picks up production a month from now. There is deliberately no pass that assigns real due dates in bulk.
    - **Graduation is derived, which makes already-finished words the real hazard.** `isVocabFullyMastered` is recomputed, not stored, so an unmastered production entry silently un-graduates every word a user ever skipped or completed and returns the whole pile as production reviews. Two separate places had to prevent this: the migration grandfathers `stage === 'graduated'` words as production-mastered, and `applyVocabIntroChoice`'s `'skip'` path (the one path that writes `'graduated'` directly) masters production alongside reading and meaning. Skip is how users say "I already know this word", so that pile is typically the largest one in the queue.
    - **A word must not be re-opened by the answer that finished it.** `applyAnswer` checks mastery *excluding* production before seeding and skips activation when the word is already fully mastered in the directions it was being trained in. Found by two existing tests failing (`graduates a vocab on reading mastery alone when meaning quizzes are disabled`, `should NOT graduate until BOTH are mastered`): seeding unconditionally meant the very answer that would have graduated a word instead attached a fresh unmastered entry to it, which is the same release-day wave arriving one word at a time. The fix preserves both invariants rather than the tests being relaxed to fit.
    - **Seeded strength comes from the meaning entry at 0.4, not from zero.** Production is harder than recognition so it is well under parity, but starting a half-known word from scratch would inflate exactly the backlog the lazy activation exists to spread out.
    - **`QuizType` stopped being a two-way union, which makes ternaries actively wrong rather than merely incomplete.** `quizType === 'reading' ? reading : meaning` routes every production answer into the **meaning** entry, corrupting its schedule with no type error anywhere. Converted to keyed lookups in `applyAnswer` and in `useQuizOrchestration`'s mastery-delta computation. Worth checking first in any future change that adds a fourth type.
    - **Deliberately left out of the knowledge curve.** That scale is normalised so a word mastered in both directions is worth exactly 200; including production would move the ceiling to 300 *and* retroactively credit ~100 points, dated at each word's introduction, to every grandfathered word - rewriting history rather than recording learning. Daily activity does include `production.history`, since those are reviews that actually happened.
    - Cross-device sync merges the entry independently (like reading and meaning), but only when at least one side actually has it, so a device still on an older build cannot write an inert entry back over another device's real production schedule.

- **[2026-09-16]**:
  - **Per-session quiz cap (`CONSTANTS.srs.sessionQuizCap`, 200), composed evenly across quiz types.** Motivated by an upcoming English-meaning-to-Japanese-reading production quiz: adding a third vocab quiz type would raise a large backlog's daily workload outright, so the session needed a real bound *before* that type exists. Three findings worth keeping:
    - **`session.committed` was bookkeeping, not a gate.** It already snapshotted every task due at session start, but `selectNextView` picked the next card from the live `learningQueue` and ignored it entirely, so it only ever fed the progress counter's denominator. Capping the snapshot alone would therefore have shrunk the displayed `n/total` while the user was still served every due card. The real change was promoting it to the authoritative work list (`getNextVocabToStudy`'s new `allowed` parameter); the cap itself is a few lines on top of that.
    - **A prefix of the snapshot is the wrong truncation.** `getNextVocabToStudy` clears every actionable reading before any meaning, so taking the first 200 keys of a 400-task snapshot yields 200 readings and zero meanings, session after session, with the meaning backlog growing monotonically. `capSessionCommit` buckets by quiz type and fills smallest-pool-first so short pools spill their unused share to the others. Ordering within the session is deliberately left alone: the reading-then-meaning batching and its `preferredType` stickiness exist so the user does not switch mental modes card-to-card, so the quota governs *composition*, not sequence.
    - **Bounding selection needs an explicit exit state, and that state must not end the session.** With selection restricted to `committed`, clearing it while capped-out work is still due leaves `sessionState` at `'review'` (computed off the live queue) and `queueItem` at null, which parks `VocabQuizScreen` on its loading gate forever. Hence `'session-complete'`. The non-obvious half: `sessionActive` must still count it as active. Ending the session there would immediately re-satisfy `useSessionLifecycle`'s start condition and commit a fresh capped set on the spot, which reduces the cap to invisible internal batching, so continuing is an explicit user action (`actions.startNewSession`). `getNextVocabToStudy` also stops short of its new-intro branch in this state rather than starting the user on new vocabulary while reviews they were never offered are due.
    - Ordering constraint worth not reintroducing: the cap runs **after** `filterSessionCommit`, which drops a vocab's meaning task when its reading is committed too. Quotas computed over that filter's input would under-fill the meaning bucket by exactly the number it was about to remove.
    - Deliberately **not** applied to the grammar activity (`GrammarSessionState` excludes `'session-complete'`): a grammar point has one quiz type, so there is nothing to balance and no starvation to prevent.

- **[2026-09-02]**:
  - **SEO investigation, and shipping gokan-dictionary as a subfolder of gokan-srs.com** (issue #19): the app ranked for the branded query "gokan" but for nothing else. Diagnosis: on-page SEO in `apps/gokan-srs/index.html` (meta, Open Graph, JSON-LD, `<noscript>` fallback) was already fine and was **not** the problem. The site had exactly **two indexable URLs** (`/` and `/about`, the only entries in `public/sitemap.xml`), which cannot compete for head terms like "learn japanese vocabulary" against sites with thousands of pages and thousands of referring domains. Ranking for "gokan" only means the homepage is indexed - a branded query with no competition is the baseline, not evidence SEO works. Meanwhile the ~39k entities the dataset already holds were invisible: the app's own `/vocab/:id`, `/kanji/:character` and `/grammar/:grammarId` routes are client-rendered, absent from the sitemap, and unlinked from any crawlable HTML. Conclusion: the fix is page inventory (what `gokan-dictionary` exists for) plus off-page authority, not further meta tuning.
    - **Subfolder over subdomain**: served at `gokan-srs.com/dictionary/`, not `dictionary.gokan-srs.com`. Google treats the two roughly equally *for an established domain*; with no backlink profile yet, consolidating every signal onto one hostname is worth more, and the dictionary's entire purpose is to accumulate authority that also lifts the app. Cost of the choice, accepted deliberately: a CloudFront behavior has to carve `/dictionary/*` out of the SPA fallback, and a `BASE_PATH` has to thread through every URL helper. `VITE_BASE_PATH=''` reverts to a bare-origin build if this is ever revisited.
    - **Two traps found while wiring the shared bucket**, both silent failures that a future change could easily reintroduce (each is also documented at its call site and in CLAUDE.md/GEMINI.md):
      - `aws s3 sync --delete` deletes everything in the destination absent from the source. With the dictionary under the `dictionary/` prefix of the app's own bucket, gokan-srs's existing `--delete` pass would have wiped all ~39k dictionary pages on **every** app deploy, reporting success. Hence `--exclude "dictionary/*"` there, and hence only the dictionary's first sync pass carries `--delete` (a `--delete` pass combined with `--exclude`/`--include` treats every filtered-out file as absent from the source).
      - An OAC origin reaches S3 through the **REST** endpoint, which does no directory-index resolution, unlike the S3 *website* endpoint. Since the dictionary emits `<path>/index.html` per entry, `/dictionary/vocab/1589350/` would have 404'd, been swallowed by the SPA `custom_error_response`, and served the SRS app for every dictionary page. Fixed with a CloudFront Function on that behavior. `default_root_object` does not help; it only applies to `/`.
    - **Known limitation, accepted**: `custom_error_response` is distribution-wide in CloudFront, so a genuinely missing `/dictionary/*` URL returns the SPA shell with a 200 (a soft 404). Every dictionary URL is generated and sitemap-listed, so this is only reachable via a stale link after a dataset change. The proper fix moves the SPA fallback off `custom_error_response` into a function on the default behavior, which is a riskier change to live app routing than the problem currently warrants.
    - **One deploy workflow for both apps and both environments** (`deploy-site.yml`, called by `deploy.yml` and `deploy-staging.yml`): the shared-datasource property was already structural (the dictionary's `resolveCompiledDir()` reads the same `apps/gokan-srs/dataset/compiled` submodule checkout gokan-srs syncs from, and one submodule pin per commit means one dataset version), so there was never dataset *duplication* to remove. What a single workflow actually prevents is drift **in time**: two workflows could deploy the app from one commit and the dictionary from another. Note the two apps consume the dataset differently - gokan-srs ships it as runtime JSON, the dictionary bakes it into HTML at build time and ships only `data/search.json` - so the same dataset change means an incremental file sync for one and a full 38,871-page regeneration (~80s locally) for the other.
    - **Staging gets `X-Robots-Tag: noindex, nofollow`** across the whole site. `staging.gokan-srs.com` serves the same built `robots.txt` as production, so `robots.txt` alone could not keep crawlers out, and a second complete crawlable copy of ~39k pages would have been a worse duplicate-content problem than the one the dictionary exists to solve.
    - **Grammar pages added** (755 points, previously unimplemented): chosen as the highest-value addition to the existing branch because grammar queries are strong long-tail targets and the data was already compiled. Example sentences render word-by-word so every dataset-resolved word links to its vocab page, which is what makes the ~36k vocab pages crawler-reachable at all; a separate `/dictionary/grammar/` index puts every grammar page at crawl depth 2 rather than leaving them sitemap-only orphans.
    - **Expectation setting**: 38,871 near-identically-structured pages from a domain with no backlinks is the shape Google treats as thin content. A fraction will be indexed, slowly. This is still worth doing, but the fewer/richer kanji and grammar pages will likely carry more weight than the long vocab tail, and backlinks remain the actual bottleneck for anything competitive.

- **[2026-08-09]**:
  - **Grammar grading made pattern-primary; positive-only vocab cross-crediting; session gains/losses summary** (issue #33 follow-up, from user report that grading was too severe): a grammar card blanks the grammar-pattern markers (PRIMARY) plus, as secondary reinforcement, any vocab the user already knows. The old `gradeGrammarAnswers` combined **all** blanks worst-of into the point's single SRS result, so one missed vocab word forced the whole grammar point to `wrong` (-0.40) even when the grammar core and every other word were right - a false negative on the exact thing the quiz exists to measure. The dataset already distinguishes the two (`GrammarExample.patternWordIndices`), but the grading flattened that distinction away.
    - **Decision (chosen by the user from three offered options)**: a *vocab coefficient*, not a discrete downgrade. The point's result is now decided by the **pattern-marker blanks alone** (`overall` = worst-of the pattern blanks; a vocab miss can never make a demonstrated grammar core `wrong`), and the vocab blanks instead scale the *reward*: `gradeGrammarAnswers` returns a `strengthDeltaModifier` in `[GRAMMAR_VOCAB_COEFF_FLOOR (0.5), 1]` = `floor + (1 - floor) * vocabCorrectRatio`, applied only when the pattern succeeded. So "grammar right, all vocab wrong" is still a success worth half the strength gain; "grammar right, all vocab right" is full gain. Rationale: there is one `SRSEntry` per grammar point, so its schedule must mean grammar-point recall - vocabulary that happens to sit in the sentence should modulate, not define, it.
    - **Plumbing**: `computeBlankPlan` now emits `isPatternBlank: boolean[]` (pattern markers vs. secondary vocab; all-false on the ~1.9% fallback examples with no located pattern, which keep the original worst-of-all grading at full strength). `SRSService.calculateNextState` gained an optional trailing `strengthDeltaModifier` (default 1.0, so vocab behaviour and all existing tests are untouched) that scales the `resultFactor * L * D` strength delta; `GrammarSRSService.applyAnswer` forwards it. Auto-advance now fires only when *every* blank was strictly correct (not just `overall === 'correct'`), so a pattern-correct card with a missed vocab blank pauses for review instead of skipping past the mistake.
    - **Positive-only vocab credit** (also user-chosen): the non-pattern blanks the user answered correctly (without revealing the hint) feed that word's own reading `SRSEntry` via the new `GrammarSRSService.applyVocabReinforcement` - a correctly recalled word in a grammar sentence is a real reading review. Positive-only by construction: credits are pre-filtered to correct/minor_error and a word absent from `learningQueue` is skipped, so grammar practice can lift vocab mastery but never lower it. Skipped on a grammar retry so a training-only redo can't over-credit the same words each loop.   - **Infinite auto-upload sync loop fix** (`sync-loop-investigation.md`): When logged into Google Drive, the auto-upload effect fired continuously. Three independent defects each sustained the loop, all fixed:
    - **Content oscillation (root cause)**: `migration.service.ts`'s unconditional `nextReviewAt` recompute called `vocabNextReviewAt(item)` **without settings** on every load, and `isMeaningQuizEnabled(undefined)` defaults to `true`. With `enableMeaningQuiz: false`, every localStorage/Drive hydration stamped the meaning-based due date while every merge (`mergeVocabProgress`, settings-aware) stamped the reading-based date — so each load→merge round trip genuinely changed the data. Fix: the reconcile effect now also compares **content** (via `progressUploadSignature` + `stableStringify` of settings) and skips the dispatch when the reconciled result equals live state.

    - Note: the doc's proposed fixes (independent settings versioning, settings normalization at boundaries) were **not** the root cause — settings normalization already existed (`loadSettings`/`parseEnvelope` spread `DEFAULT_SETTINGS`), and the flip came from the settings-less migration recompute, not from a partial settings blob. The version-conflation issue in `mergeSettings` call sites is real but benign for this bug; it remains a candidate for a future cleanup.
  - **Quiz-card flicker fix (deterministic queue pick)**: on app start and after each answer, several different vocab cards flashed for ~1s before the next card settled. Cause: `getNextVocabToStudy` picked from the due pool with `Math.random()`, but it runs inside `selectNextView` — recomputed on every state change, with `currentVocab` among the memo deps. Each recompute rolled a different card; loading that card changed `currentVocab`, triggering the next recompute/roll, cascading until two consecutive rolls happened to agree. Fixed by (1) replacing `pickRandom` with `pickStable` in `srs.utils.ts` — a pick seeded by a hash of the pool's own state (vocabIds + totalReviews + lastReviewedAt + needsRetry flags), so the same pool always yields the same card while every answer still naturally reshuffles (the anti-interference intent is preserved as a per-answer reshuffle instead of a per-render one); and (2) a guard in the load-vocab effect that skips `LOAD_VOCAB_START` when exactly the requested vocab/quizType/quizMode is already loaded (selectNextView returns a fresh `queueItem` object per recompute, so the effect dep alone can't detect "same card").
  - **Sync fast-forward + honest reconcile signal** (follow-up to the loop fix): after the loop was gone, each answer still caused one reconcile pass that reloaded the active quiz card. Cause: every background upload ran a full merge against the remote file — which is almost always just this client's own previous write — and a **self-merge is not a no-op** (`mergeEntry`'s `max()` safety net resurrects the pre-answer `memoryStrength` after a failed review, and `applyAnswer`'s all-false `needsRetry` object gets collapsed to `undefined`), so the merged result always differed from live state and `RECONCILE_REMOTE` fired. Two changes:
    - `GoogleDriveSync.sync()` now **fast-forwards**: it remembers the content signatures (`progressUploadSignature`/`stableStringify`) of the envelope it last wrote; when the remote file still matches them, local state is a strict descendant and the merge is skipped entirely — local content is uploaded as-is with a version bump. Side benefit: a wrong answer's SRS penalty is no longer partially undone by the routine sync that follows it (the `max()` resurrection). Full merge still runs whenever remote content genuinely diverges (another device wrote).
    - `sync()` returns a `SyncOutcome { envelope, pulledRemoteChanges }`, and `GoogleDriveContext` bumps `lastBackgroundMergeTime` **only when `pulledRemoteChanges` is true** — matching that field's documented meaning ("bumped after a background sync that pulled in remote changes"). Routine answer uploads therefore never trigger the reconcile effect at all; the quiz session is only disturbed when another device's changes actually arrive.
    - Cleanup: the redundant post-merge content-signature guard in the reconcile effect was removed (the `pulledRemoteChanges` gate + version guard are sufficient; three overlapping gates on one decision is how the original drift accumulated). A `console.info` diagnostic fires when fast-forward misses despite a prior write — if it appears after every answer, suspect a broken serialize→parse round trip. Deeper structural follow-ups (derive `nextReviewAt`/`stage` at read time instead of persisting them, SyncManager extraction out of React, Drive revision-id ancestry, `mergeEntry` max() policy) are documented in `FUTURE_REFACTORS.md`.
